# Project instructions

## General 
Use an academic writing and coding style. Avoid stating obvious or common-sense points unless they are necessary to support the argument.

## Git
Read-only. You may run `git status`, `git diff`, `git log`, `git show`, `git blame`.
Never stage, commit, push, merge, rebase, checkout, or stash.
When work is ready to commit, tell me what changed and let me do it.
After each change write a commit for me but do not run it

## Comments
- One line where possible. Two at most.
- Explain why, not what — skip comments that restate the code.
- No multi-line block comments or section banners.
- Docstrings: one sentence summary. Add params/returns only when the types
  don't make it obvious.
- Don't add comments to code you didn't change.

## Prose (docs, READMEs, changelogs — not code comments)

Voice
- Vary sentence length. Short declarative sentences are fine; long ones need a reason.
- Plain verbs, no decorative phrasing.
- Don't inflate the subject: no "turning point", "vital role", "lasting legacy",
  "far-reaching impact", "a testament to".
- Don't tack interpretation onto a sentence that doesn't need it — no "highlighting
  the importance of", "underscoring its role".
- "Not only... but also" only for a real contrast.

Words to avoid
landscape, crucial, key, multifaceted, intricate, dynamic, valuable, prominent,
enhance, foster, commitment, innovative, transformative, showcase, testament.
Use one only if it's genuinely the clearest word available.
Repeat a precise word rather than reaching for a vague synonym.

Structure
- Open on the actual subject. No preamble about why it matters.
- Every paragraph needs a point. No disposable opening lines.
- Don't force examples into threes. Use as many as the content has.
- Go easy on "Additionally", "Furthermore", "On the other hand", "Ultimately",
  "It is worth noting".
- Don't repeat the same idea in the opening, the body, and the ending.
- End where the content ends. No summary paragraph, no optimistic closer.
- No "Conclusion", "Challenges and Opportunities", or "Future Outlook" headings
  unless the content is actually organized that way.
- Prose by default. Lists only when the content is genuinely a list.

Facts
- Never invent numbers, dates, names, quotes, or sources. Mark gaps as
  [accurate information needed] and leave them.
- No "experts believe", "studies show", "critics argue" without a named source.
- When I give you a source, claim only what that source supports.

Formatting
- No emoji, no `---` dividers, minimal bold, no tables unless the data is tabular.
- Em dashes, colons, parentheses only when they improve clarity.

Never
- "Certainly", "Here is the text", "I hope this helps", "Let me know if you need
  anything else".
- Don't add deliberate typos or awkward grammar to sound human.
- Don't invent experiences or opinions I didn't give you.
